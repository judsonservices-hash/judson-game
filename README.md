# Deep Tide — Roblox project

This is the code foundation for **Deep Tide**, our underwater fishing-and-diving game: you dive
deeper to catch rarer fish, sell your catch, and upgrade gear to reach the abyss.

It is a **Rojo + Knit** project. It boots cleanly, and it now ships a **playable world**: pressing
Play puts you on a real dock in a real reef, with the Shallows below and the gated Shelf beyond
the Rim Gate. The gameplay itself (rod handling, the catch mini-game, fish AI, sell, upgrade) is
still clearly-marked `TODO` slots for the next developer; the world, the spawn anchors it spawns
fish into, and player-data persistence are done.

---

## 1. The fastest way to see it run (no tools to install)

1. Open **`build/deep-tide.rbxlx`** — double-click it, or in Roblox Studio use
   *File → Open from File…* and pick that file.
2. Press **Play** (F5).

You spawn at **(0, 8, −20)** standing on the Deep Tide dock, facing the water (+Z), with a
`DIVE HERE` marker at the ramp edge in front of you, the Rod Rack and the Tide Trader stall on the
deck, the reef and the Trawler wreck below, and the Rim Wall closing the north end of the Shallows.
Swim north through the Rim Gate and you are in The Shelf — darker, colder, and twice as deep.

The world is **not** in the place file: it is built at server start by `WorldService` from the
config tables, so the numbers in `src/shared/Config/` are the single source of truth. You should
see exactly two lines in the **Output** window:

```
[Deep Tide] world built in 4 ms — 278 parts (Shallows 122, Rim 54, Shelf 90) + Spawns 11, Water 1 · 34 spawn anchors · 0 layout problems
[Deep Tide] v0.1.0 booted — 9 services · config OK — 5 species, 74 fish live, 278 world parts · 12 remotes · persistence: session-only
```

Those lines are the proof it booted: nine server services registered with Knit, the config tables
validated against the design document, the world built and self-checked against the same config,
and all twelve network events created.

## 2. The development workflow (Rojo live-sync)

Editing files in `src/` and having Studio update instantly is the normal way to work here.

1. **Install Rojo** (the tool that turns this folder into a Roblox place). Easiest:
   * install [Aftman](https://github.com/LPGhatguy/aftman) then run `aftman install`, **or**
   * download the Rojo release for your OS from <https://github.com/rojo-rbx/rojo/releases>
     (Windows: `rojo-x.y.z-windows-x86_64.zip`) and put `rojo.exe` on your PATH.
2. **Install the Rojo Studio plugin**: in Studio, *Plugins → Manage Plugins →* search
   **Rojo** (or *Toolbox → Plugins*). One-time step.
3. In a terminal, from this folder, run:

   ```
   rojo serve
   ```

   It prints something like `Rojo server listening on 127.0.0.1:34872`.
4. In Studio: open an empty **Baseplate** place, click **Rojo** on the Plugins toolbar, press
   **Connect**.
5. Press **Play**. Your edits in `src/` now flow into Studio within a second; the Rojo panel
   shows a green dot when connected. (`WorldService:Build()` re-runs on every Play, so world
   edits appear without touching the place file.)

**Rebuilding the place file yourself** (after you change `default.project.json`):

```
rojo build default.project.json -o build/deep-tide.rbxlx
```

> The Rojo server address is a local address used by the Studio plugin on your own machine.
> Nothing about it is public.

### Not using Rojo? Two fallbacks

* **Dependencies, by hand.** The project needs one library, Knit. It is already inside this
  repo at `vendor/Knit-1.7.0.rbxm` and the project maps it into the right place. If you ever
  build by hand in Studio instead: insert `vendor/Knit-1.7.0.rbxm` into **ReplicatedStorage**
  and rename the resulting folder to **Packages**, so that
  `ReplicatedStorage.Packages.Knit` is a ModuleScript.
* **Wally, if you prefer a package manager.** `wally.toml` is committed with
  `Knit = "sleitnick/knit@1.7.0"`. Run `wally install`, then build with
  `rojo build wally.project.json -o build/deep-tide.rbxlx` (that project file maps Wally's
  `Packages/` folder instead of the bundled model). `Packages/` is not committed — it is
  regenerated by Wally.

## 3. Testing without Studio

`tools/worldtest/` runs the real server code headlessly, against a stub of the Roblox globals, in
the [Luau CLI](https://github.com/luau-lang/luau). No Studio, no place file, no API access needed.

```
tools/worldtest/check.sh          # all three suites (93 assertions)
tools/worldtest/check.sh world    # the world build: counts, flags, idempotency, water, spawn
tools/worldtest/check.sh persist  # player-data persistence via a mock DataStore
tools/worldtest/check.sh config   # runs ConfigCheck over every config table
```

It catches the things a playtest only shows you five minutes later: a landmark whose built part
count drifted from `LandmarkConfig`, a part placed outside `ZoneConfig.BuildZone`, a duplicate
part name, a decorative part that is still hit-testable, a world that duplicates itself when it
rebuilds, or a DataStore path that errors when API access is off. The suites are also the fastest
way to see the whole world tree as data — the world suite prints every folder with its part count.

## 4. Saving player data

Coins and the catch log **are saved** through Roblox DataStores: loaded on join, saved on leave,
and saved again once more on shutdown. **In Studio this needs API access turned on**, once:

> Studio → **Game Settings → Security → Enable Studio Access to API Services**

Until that is on (or on any machine where Roblox data services are unavailable), the game still
runs perfectly — the boot line says `persistence: session-only` and progress simply is not kept
between sessions. A save failure can never break the game or lose a caught fish; that is deliberate
(the design document requires it), and every DataStore call is wrapped so it cannot error the loop.

Services that hold per-player state should define `ReleasePlayer(player)` — `PlayerService` calls
it on every sibling service when a player leaves, so nothing leaks between sessions.

## 5. Publishing to Roblox — this part is yours

Building and publishing happen in your own Roblox account, not in this repo. When you want the
game live:

1. Open `build/deep-tide.rbxlx` (or connect with Rojo, see §2) in Roblox Studio.
2. *File → Publish to Roblox As…* — choose **Create new experience**, and name it **Deep Tide**.
3. Set the place's details (icon, description, genre) in *Game Settings*, and enable
   *Security → Enable Studio Access to API Services* (§4).
4. To update later: repeat *File → Publish to Roblox* on the same place.
5. If you later want a Roblox **group** instead of your personal account (recommended before
   monetisation), publish to the group from the same dialog.

Nothing here reads Robux: there is no monetisation code yet, by design.

## 6. Where everything lives

```
default.project.json      what maps to what inside the place (the world itself is built at runtime)
wally.project.json        same, but with dependencies coming from Wally's Packages/ folder
wally.toml / wally.lock   dependency manifest (Knit 1.7.0)
vendor/Knit-1.7.0.rbxm    offline copy of Knit, so the project builds with zero tooling
build/deep-tide.rbxlx     the built place you can open directly
tools/worldtest/          headless test rig for the world build, persistence and config (§3)
src/shared/               -> ReplicatedStorage.DeepTide   (data + shared modules)
  Config/                 every gameplay AND world number, as pure data:
    FishConfig            five species: rarity, value, depth band, counts, mini-game tuning
    SpawnConfig           the fixed spawn coordinates for every fish (§4.6)
    LandmarkConfig        landmark anchors, per-group part counts, the world part budget
    RarityConfig          the rarity enum, colours, hook windows, strain multipliers
    RodConfig             Rusty Rod / Brass Rod (cost, line strength, rarity gate, modifiers)
    GearConfig            Rubber Lungs / Reinforced Tank (air capacity, depth rating)
    DiveConfig            swim speeds, air threshold, auto-surface rule, refill time
    FightConfig           the tension mini-game constants, cooldowns, failure messages
    EconomyConfig         starting cash, sell values, shop, targets, balance maths
    ZoneConfig            water region, zones, the Rim Gate, the seabed grids, fog curve
  Modules/
    Types                 shared type definitions
    Remotes               the twelve network events, declared once
    Configs               single entry point: Config.Fish, Config.Economy, …
    ConfigCheck           runs at boot; warns if a config edit breaks a design relationship
src/server/               -> ServerScriptService.DeepTide   (Knit services, 9)
  init.server.luau        the boot: creates remotes, registers services, starts Knit
  Services/               WorldService, PlayerService, EconomyService, InventoryService,
                          GearService, ShopService, FishService, FishingService, DiveService
                          WorldService builds the whole world from config at start (see §7)
  Modules/PlayerStore     the DataStore save/load wrapper
src/client/               -> StarterPlayerScripts.DeepTide  (Knit controllers, 5)
  init.client.luau        the client boot
  Controllers/            RodController, FishingController, HudController, ShopController,
                          DepthController
```

Rules the code follows, so it stays easy to work on:

* **No gameplay number ever lives in gameplay code.** They all live in `src/shared/Config/`,
  each file headed with the section of the design document it came from.
  `ConfigCheck` (see the boot line) catches it if two tables ever disagree.
* **World geometry is data too.** `WorldService` holds only the per-piece *recipe* (sizes,
  colours, tilts); every position, count and volume comes from `LandmarkConfig`, `ZoneConfig`
  and `SpawnConfig`. Editing a part count in `LandmarkConfig` and rebuilding is the whole workflow.
* **The server decides.** Client scripts send requests and draw what they are told.
* **Services and controllers hold wiring and typed signatures only.** Search for `TODO` to find
  every slot waiting for gameplay code; each one names the design-document section it comes from.

## 7. The world (`WorldService`)

`WorldService:KnitInit()` calls `Build()`, which **clears and rebuilds** `Workspace.DeepTide.World`,
`.Water` and `.Spawns` — so a server restart or a second call rebuilds rather than duplicating, and
`.Fish` (runtime fish, `FishService`) is never touched. The tree it produces:

```
Workspace/DeepTide/
  World/Shallows/Base        24 sand Parts — the seabed grid, the SE trench, §3.1
  World/Shallows/L1..L9      L1 Deck/Pylons/Ramp/LightTower/Beacon, L2 Coral Spire,
                             L3 Trawler, L4 Kelp Field (30 fronds), L5 Deep Hole,
                             L6 Sand Channels, L7 Fish Rocks, L9 Buoys   (L8 = 0 parts)
  World/Rim/R1..R3           R1 Rim Wall (8 terraces), R2 The Rim Gate, R3 Rim Current
  World/Shelf/Base           20 rock Parts — the shelf floor, sloping to the chasm
  World/Shelf/S1..S6         S1 The Lip, S2 Crevice Row (eel dens), S3 Ghost Ledge,
                             S4 Thermal Vents, S5 Sunken Pillars, S6 The Chasm
  Water/WaterRegionMarker    invisible volume marker; the water itself is Terrain, §3.0
  Spawns/SpawnLocation       the player spawn, on the deck, facing the water
  Spawns/L1_RodRack          + L1_RodRack_Top, L1_TideTrader, L1_TideTrader_Sign, DiveMarker
                             (L1's four prompt-host props, Appendix A) — each with its
                             ProximityPrompt already built; their verbs are the services' TODOs
  Spawns/<Species>           one invisible *_AnchorHost part per species, holding one
                             Attachment per §4.6 coordinate (34 anchors in total), each
                             carrying Kind / Index / box / radius / facing as attributes
  Fish/                      empty — runtime fish only, owned by FishService
```

Every part is `Anchored`, `CanTouch = false`; decorative geometry (kelp, neon, the dive marker,
the water marker) is also `CanCollide = false` and `CanQuery = false` so it is never hit-testable.
Naming follows Appendix A (`<ID>_<Piece>`, e.g. `L1_Deck`, `R2_Pillar_W`, `S6_Wall_E_1_2`), and
names are asserted unique — a scripter can find any volume by name.

`WorldService` also answers `GetZoneAt(position)`, `GetZoneForDepth(depthStuds)`,
`GetInteractionPoint(name)`, `GetSpawnPosition()`, `GetPrompt(id)`, `GetAnchorFolder(species)`,
and `ValidateLayout()` — the same check the build runs on itself, which returns a list of
problems (landmark counts vs `LandmarkConfig`, the build-zone rule, duplicate names, anchor
counts). A broken edit shows up as a `[Deep Tide] world: …` warning at boot instead of a wrong
world at playtest time.

Known deviations from the design document are listed in the GDD's Appendix A under **As built**:
the dock ramp angle, the cone-less spire/chimneys, the eel den speck, and the fact that the Rim
Gate is a geometric read while the hard gate is the DepthRating rule (§5.4).

## 8. Not built yet (on purpose)

1. the gameplay: rod handling, the tension mini-game, fish behaviour, selling, upgrades
   (`TODO`s in `FishingService`, `FishService`, `EconomyService`, `InventoryService`,
   `GearService`, `ShopService`, `DiveService` and the five controllers);
2. the art pass: lighting, fog, the underwater colour grade, sun shafts, particles (Technical
   Artist), and the HUD / shop screens (UI/UX);
3. the landing page for the game.

The design document is `../gdd-mvp.md` and it is the input of record: if a number is needed
that is not in `src/shared/Config/`, the answer is in the GDD, not in a new constant.
