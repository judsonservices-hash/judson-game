# Deep Tide — Roblox project scaffold

This is the code foundation for **Deep Tide**, our underwater fishing-and-diving game: an
underwater fishing-and-diving game where you dive deeper to catch rarer fish, sell your catch,
and upgrade gear to reach the abyss.

It is a **Rojo + Knit** project. Everything the game will need is wired up and boots cleanly;
the actual gameplay (rod, catch mini-game, fish AI, sell, upgrade) is deliberately left as
clearly-marked `TODO` slots for the next developer.

---

## 1. The fastest way to see it run (no tools to install)

1. Open **`build/deep-tide.rbxlx`** — double-click it, or in Roblox Studio use
   *File → Open from File…* and pick that file.
2. Press **Play** (F5).

You will spawn on a small wooden pad above the water. That is expected: this is the *code*
scaffold, not the finished world. You should see exactly one line in the **Output** window:

```
[Deep Tide] v0.1.0 booted — 9 services · config OK — 5 species, 79 fish live, 226 world parts · 12 remotes · persistence: session-only
```

That line is the proof the scaffold booted: nine server services registered with Knit, the
config tables validated against the design document, and all twelve network events created.

## 2. The development workflow (Rojo live-sync)

Editing files in `src/` and having Studio update instantly is the normal way to work here.

1. **Install Rojo** (the tool that turns this folder into a Roblox place). Easiest:
   * install [Aftman](https://github.com/LPGhatguy/aftman) then run `aftman install`, **or**
   * download the Rojo release for your OS from <https://github.com/rojo-rbx/rojo/releases>
     (Windows: `rojo-x.y.z-windows-x86_64.zip`) and put `rojo.exe` on your PATH.
2. **Install the Rojo Studio plugin**: in Studio, *Plugins → Manage Plugins →* search
   **Rojo** (or *Toolbox → Plugins*). One-time step.
3. In a terminal, from this folder, run:

   ```
   rojo serve
   ```

   It prints something like `Rojo server listening on 127.0.0.1:34872`.
4. In Studio: open an empty **Baseplate** place, click **Rojo** on the Plugins toolbar, press
   **Connect**.
5. Press **Play**. Your edits in `src/` now flow into Studio within a second; the Rojo panel
   shows a green dot when connected.

**Rebuilding the place file yourself** (after you change `default.project.json`):

```
rojo build default.project.json -o build/deep-tide.rbxlx
```

> The Rojo server address is a local address used by the Studio plugin on your own machine.
> Nothing about it is public.

### Not using Rojo? Two fallbacks

* **Dependencies, by hand.** The project needs one library, Knit. It is already inside this
  repo at `vendor/Knit-1.7.0.rbxm` and the project maps it into the right place. If you ever
  build by hand in Studio instead: insert `vendor/Knit-1.7.0.rbxm` into **ReplicatedStorage**
  and rename the resulting folder to **Packages**, so that
  `ReplicatedStorage.Packages.Knit` is a ModuleScript.
* **Wally, if you prefer a package manager.** `wally.toml` is committed with
  `Knit = "sleitnick/knit@1.7.0"`. Run `wally install`, then build with
  `rojo build wally.project.json -o build/deep-tide.rbxlx` (that project file maps Wally's
  `Packages/` folder instead of the bundled model). `Packages/` is not committed — it is
  regenerated by Wally.

## 3. Saving player data

Coins and the catch log are saved through Roblox DataStores. **In Studio this needs API access
turned on**, once:

> Studio → **Game Settings → Security → Enable Studio Access to API Services**

Until that is on (or on any machine where Roblox data services are unavailable), the game
still runs perfectly — the boot line says `persistence: session-only` and progress simply is
not kept between sessions. A save failure can never break the game or lose a caught fish;
that is deliberate (the design document requires it).

## 4. Publishing to Roblox — this part is yours

Building and publishing happen in your own Roblox account, not in this repo. When you want the
game live:

1. Open `build/deep-tide.rbxlx` (or connect with Rojo, see §2) in Roblox Studio.
2. *File → Publish to Roblox As…* — choose **Create new experience**, and name it **Deep Tide**.
3. Set the place's details (icon, description, genre) in *Game Settings*, and enable
   *Security → Enable Studio Access to API Services* (§3).
4. To update later: repeat *File → Publish to Roblox* on the same place.
5. If you later want a Roblox **group** instead of your personal account (recommended before
   monetisation), publish to the group from the same dialog.

Nothing here reads Robux: there is no monetisation code in the scaffold, by design.

## 5. Where everything lives

```
default.project.json      what maps to what inside the place (edit this to add world parts)
wally.project.json        same, but with dependencies coming from Wally's Packages/ folder
wally.toml / wally.lock   dependency manifest (Knit 1.7.0)
vendor/Knit-1.7.0.rbxm    offline copy of Knit, so the project builds with zero tooling
build/deep-tide.rbxlx     the built place you can open directly
src/shared/               -> ReplicatedStorage.DeepTide   (data + shared modules)
  Config/                 every gameplay number, as pure data:
    FishConfig            five species: rarity, value, depth band, counts, mini-game tuning
    SpawnConfig           the fixed spawn coordinates for every fish
    LandmarkConfig        landmark anchors and part counts for the world build
    RarityConfig          the rarity enum, colours, hook windows, strain multipliers
    RodConfig             Rusty Rod / Brass Rod (cost, line strength, rarity gate, modifiers)
    GearConfig            Rubber Lungs / Reinforced Tank (air capacity, depth rating)
    DiveConfig            swim speeds, air threshold, auto-surface rule, refill time
    FightConfig           the tension mini-game constants, cooldowns, failure messages
    EconomyConfig         starting cash, sell values, shop, targets, balance maths
    ZoneConfig            water region, zones, the Rim Gate, fog curve
  Modules/
    Types                 shared type definitions
    Remotes               the twelve network events, declared once
    Configs               single entry point: Config.Fish, Config.Economy, …
    ConfigCheck           runs at boot; warns if a config edit breaks a design relationship
src/server/               -> ServerScriptService.DeepTide   (Knit services, 9)
  init.server.luau        the boot: creates remotes, registers services, starts Knit
  Services/               PlayerService, EconomyService, InventoryService, GearService,
                          ShopService, FishService, FishingService, DiveService, WorldService
  Modules/PlayerStore     the DataStore save/load wrapper
src/client/               -> StarterPlayerScripts.DeepTide  (Knit controllers, 5)
  init.client.luau        the client boot
  Controllers/            RodController, FishingController, HudController, ShopController,
                          DepthController
```

Rules the code follows, so it stays easy to work on:

* **No gameplay number ever lives in gameplay code.** They all live in `src/shared/Config/`,
  each file headed with the section of the design document it came from.
  `ConfigCheck` (see the boot line) catches it if two tables ever disagree.
* **The server decides.** Client scripts send requests and draw what they are told.
* **Services and controllers hold wiring and typed signatures only.** Search for `TODO` to find
  every slot waiting for gameplay code; each one names the design-document section it comes from.

## 6. Not built yet (on purpose)

The scaffold stops at the code foundation. Still to come, in order:

1. the world itself: seabed, reef, Rim wall, Shelf, terrain water (the blockout), and the
   Rod Rack / Tide Trader / dive-marker props with their prompts;
2. the gameplay: rod handling, the tension mini-game, fish behaviour, selling, upgrades;
3. lighting, fog and effects; the HUD and shop screens; the landing page.

The spawn pad in `Workspace.DeepTide.Spawns.SpawnLocation` is a **stand-in** for the dock deck —
the world build replaces it with the real dock part at the same coordinates.

## 7. Notes for the team

* The design document is `../gdd-mvp.md` and it is the input of record: if a number is needed
  that is not in `src/shared/Config/`, the answer is in the GDD, not in a new constant.
* Two deliberate deviations from the design document's appendices are recorded in code
  comments: `SpawnConfig` and `LandmarkConfig` exist as separate data files (the appendices
  named their contents but not their files), and the built place loads the committed Knit
  bundle model instead of requiring Wally.
* The design document quotes "~280 parts" for the world, but the per-landmark counts in its own
  tables sum to 226. `LandmarkConfig` carries both numbers; the build should be measured, not
  assumed.
